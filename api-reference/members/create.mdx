---
title: "Create Member"
openapi: "POST /v1/members"
description: "Create a member in the chapter."
---

Create a member in the chapter. If `password` is omitted a random one is generated. Executive notifications fire as if the key's owner had created the member in the app.

**Required scope:** `members:write`

## Put them through the chapter's onboarding

Send `membership_type_id` and the new member goes through your chapter's normal joining process, exactly as if an administrator had added them in the app:

- an **application** is raised and sits in **Admin → Workflow**, waiting for payment or for approval (whichever your membership type is set up to do),
- any **onboarding dues** are created against the member,
- and your **chapter administrators are notified** of the new application.

The member stays inactive until the application is approved and paid — so this is the call to use when you want the person to show up in the places your admins actually look.

Leave `membership_type_id` out and you get the older behaviour: the person and their chapter link are created, with no application and no dues.

<ParamField body="membership_type_id" type="integer">
  The membership type they are joining. Must belong to the key's chapter. Supplying it raises the application.
</ParamField>

<ParamField body="answers" type="object">
  Answers to your chapter's application form, as `{ "question": "answer" }`. Defaults to your chapter's form with empty values. Only used together with `membership_type_id`.
</ParamField>

<Warning>
  If your chapter's application form has **required questions**, `answers` must include them — otherwise the call returns `400` naming the ones that are missing. Call `GET /v1/application-forms` first (see **Applications → List application form templates**) to see what your form asks for.
</Warning>

<Note>
  Email addresses are unique across Transparency Hub. If the address already belongs to somebody — including in another chapter — that person is **added to this chapter** instead of being created again, and the reply is `200` rather than `201`. If they are already in this chapter you get `409` with their `member_id`. In that case they are simply linked to the chapter and **no application is raised**, even if you sent `membership_type_id` — raise it for them through the app.
</Note>

<RequestExample>
```json Request
{
  "firstname": "Ada",
  "lastname": "Lovelace",
  "email": "ada@example.org",
  "title": "Mr",
  "country": "NG",
  "membership_type_id": 3,
  "answers": {
    "profession": "Engineer",
    "graduation_year": "2010"
  }
}
```
</RequestExample>

<ResponseExample>
```json 201
{
  "status": "success",
  "data": {
    "id": 42,
    "title": "Mr",
    "firstname": "Ada",
    "lastname": "Lovelace",
    "email": "ada@example.org",
    "country": "NG",
    "profilepic": null,

  }

```
</ResponseExample>

<Tip>
  To follow the application afterwards, call `GET /v1/applications?member_id=42` (see **Applications → List applications**).
</Tip>
